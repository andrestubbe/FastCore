# .TODO.md — FastCore Architecture Roadmap: Modernizing to Java 21+ FFM (Foreign Function & Memory API)

## 🎯 Strategisches Ziel
Ablösung des veralteten, trägen JNI (aus Java 1.1 / 1997) durch die moderne, JIT-inlinbare **Foreign Function & Memory API (FFM)** als universelles Native-Backend für die gesamte **FastJava**-Suite.

---

## ⚡ Wird FastJava dadurch schneller? (Klare Antwort)

**JA, und zwar dramatisch – insbesondere überall dort, wo viele kleine native Aufrufe oder speicherintensive Off-Heap-Transfers stattfinden.**

### Warum FastJava durch FFM schneller wird:
1. **Zero Call Overhead (JIT-Inlining & direkte CPU-Register)**:
   - **Altes JNI**: Bei jedem Aufruf muss die JVM den Thread-Status auf Native umschalten, einen GC-Safepoint-Check machen, Register auf den Stack sichern und `JNIEnv*` / `jobject` übergeben (~15–30 ns Overhead pro Call).
   - **Neues FFM**: Der HotSpot C2-Compiler kennt die native System-ABI (Windows x64 / Linux AMD64) und übergibt Parameter direkt über CPU-Register (`RCX`, `RDX`, `R8`, `R9`). Der Overhead sinkt auf **~2–5 ns** und kann bei Hot-Loops sogar geinlined werden.
2. **Echtes Zero-Copy & GC-Freiheit**:
   - Keine temporären Puffer, kein Array-Pinning (`GetPrimitiveArrayCritical`), keine GC-Pausen.
   - Nahtlose Brücke zu **`FastPointer`** und **`FastMemory`**: Ein 64-Bit Pointer (`long`) wird ohne Konvertierung direkt als Maschinencode-Adresse in die nativen Vektor-Register (AVX2/AVX-512) geladen.
3. **Reiner C/C++ Code ohne JNI-Ballast**:
   - Native Funktionen bleiben 100% sauberer Standard-C/C++-Code (`extern "C"`). Keine `jni.h`, kein `Java_...`-Präfix, volle Portabilität zu Bibliotheken wie `llama.cpp` oder Vulkan/DirectX.

## 🧩 Auswirkungen auf die FastJava-Module

| Modul | JNI-Problem | FFM-Gewinn |
| :--- | :--- | :--- |
| **FastAIModel** | Hunderte GEMV-Calls pro Token bremsen CPU-Durchsatz | **Direkte AVX2-Vektor-Pipeline via Register (Sprung auf 15–30 tok/s)** |
| **FastGPU** | Buffer-Mapping erfordert JNI-Objektwrapping | **Zero-Copy Vulkan/CUDA Buffer Passing direkt via `MemorySegment`** |
| **FastSIMD** | JNI-Boundary verhindert Vektorisierung kleiner Chunks | **JIT kann native AVX2/AVX-512 Instruktionen direkt verketten** |
| **FastFileWatch** | Native ReadDirectoryChangesW Events müssen über JNI gemarshallt werden | **Direkte Ringbuffer-Verarbeitung im nativen Speicher** |
| **FastFileSearch** | Syscall-Overhead bei Millionen von Pfadprüfungen | **Direkter nativer Index-Zugriff ohne JVM-Stackwechsel** |

## 🛠️ Architektur-Plan: FastCore Modernisierung

### Phase 1: Validierung in FastAIModel (Aktueller Stand)
- [x] Proof-of-Concept des FFM-Backends in `fastaimodel-streaming` (`NativeGemvBackend`).
- [x] Native AVX2/FMA Kernels (`fastai_streaming_kernels.dll`).
- [x] Benchmarking gegen reine Java- und Ollama-Inferenz.

### Phase 2: FastCore Modularisierung (Java 17 vs. 21)
Da `FastCore` aktuell auf Java 17 zielt, FFM aber ab Java 21 LTS stabil ist:
- **Option A (Multi-Release JAR / Submodul `fastcore-ffm`)**:
  - Basis `FastCore` bleibt kompatibel mit Java 17 (JNI-Fallback).
  - `fastcore-ffm` wird aktiv, wenn JVM $\ge$ 21 läuft.
- **Option B (FastCore Upgrade auf Java 21 LTS)**:
  - Hebt FastCore direkt auf Java 21 LTS an (empfohlen für maximale Einfachheit und Performance).

### Phase 3: Universelle FastCore FFM-API
Bereitstellung von Standard-Helfern in `FastCore`:
```java
// Universeller nativer Funktionsaufruf ohne JNI
MethodHandle fn = FastCore.lookup("fastkernel.dll", "vector_dot", FunctionDescriptor.of(...));

// Direkte Konvertierung von FastPointer zu MemorySegment
MemorySegment seg = FastCore.asSegment(fastPointer, sizeBytes);
```
